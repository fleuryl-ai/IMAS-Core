# Report — SWMR: commit barrier + `data_raw_str` as a fixed-width string column

**Branch:** `swmr-fixed-string-col` (from `index_table_v2` @ `6fb6a9e`)
**Date:** 2026-09-06
**Status:** implemented, built clean, **67/67 CTest pass**, on-disk format re-verified with h5py.

---

## 1. Problem

`data_raw_str` — the columnar store for every string payload (metadata values, string
signals, lists of strings) — was a **variable-length (vlen) UTF-8** HDF5 datatype. A vlen
string is not a single region of the file: each element is a handle into a *separate heap*,
and its write updates (a) the heap payload, (b) the handle array in the dataset chunks, and
(c) the heap's own free-space/metadata. Under the file alignment in force
(`H5Pset_alignment(fapl, 4096, 4MB)`), those three live in **different 4 MB-aligned
extents**. An SWMR reader that observes the index row before the heap is fully published can
follow a handle into a half-written payload → torn/garbage string, or an HDF5 abort. HDF5's
documented SWMR feature does **not** cover vlen datatypes at all, so the column was the one
part of the file that could not be made SWMR-safe under the official API either.

The binding project constraint is SWMR (compact-index refactor). This column had to be
removed from that path.

## 2. Two-level diagnosis

Two independent problems were found; the first is the *more fundamental* one and had been
missed:

**(a) SWMR did not actually function — no commit barrier.** `PanzerDB::flush()`
(`panzerdb.cpp`) performed the `H5Dwrite`s into HDF5's in-memory **file image** and then
*cleared the buffers and returned*, with an explicit comment "do not force a disk flush on
every call". There was **no `H5Fflush`** anywhere in the engine's write path. A *separate*
reader process only sees writer state once it is pushed through the OS, i.e. at `close()` —
so no incremental writer progress was ever visible cross-process. The "index row = commit
point" protocol therefore held only *within a process*, not across.

**(b) The vlen column.** Even with (a) fixed, a vlen string is structurally the weakest
element for SWMR (three file regions, excluded from HDF5's SWMR). The fixed-width `paths`
column already proved the safe pattern (one fixed byte width per element, NUL-padded).

## 3. Decisions (fixed with the user)

- **String width cap:** **512 bytes** (`STRING_MAX_LEN = 512`), fixed width, NUL-padded
  `H5T_C_S1` — same pattern as `paths` (which uses `PATH_MAX_LEN = 256`). 512 was chosen
  over 256 for headroom on long IMAS metadata (descriptions, labels) while still covering
  the entire current test corpus (max string in tests ≈ 52 bytes).
- **Overflow policy:** **fail-fast, no silent truncation.** A value longer than
  `STRING_MAX_LEN - 1 = 511` bytes is rejected with an `ALBackendException` **at write
  time**, so the append buffer never holds a bad value and `close()` cannot re-throw.
- **Backward compatibility:** **clean break.** The reader expects a fixed-width 512-byte
  C1 column; there is **no vlen read fallback**. Files written by pre-change (vlen) builds
  must be regenerated by the new writer. (None of the tests relen a committed vlen `.h5` —
  every test regenerates its own corpus each run.)
- **Commit barrier:** a single `H5Fflush(file_id, H5F_SCOPE_GLOBAL)` at the end of
  `flush()` makes each commit atomically visible to other processes.

## 7. Backward-compat impact (clean break)

Pre-change files have `data_raw_str` as a **vlen** dataset; the new reader expects a fixed
512-byte C1 column and does **not** attempt a vlen read. Consequences:
- A reader of an *old* file: opening still succeeds, but reading a string leaf will fail a
  type check (vlen vs fixed 512). Those files are the **same writer generation** (pre-change)
  and must be regenerated by any process that reads strings from them.
- APPEND mode to an old vlen file: the writer now opens and would `H5Dwrite` a fixed-width
  value into a vlen chunk — HDF5 rejects the type mismatch. This is the intended clean break.

If we ever need to read legacy files, the minimal follow-up is a one-line detection at
open: `hid_t t = H5Dget_type(data_dset_str); bool legacy = t>=0 && (H5Tget_size(t)==H5T_VARIABLE);`
and branching between the old vlen read and the new fixed read.

## 8. Follow-ups

1. **AFS / shared-FS validation.** The local-POSIX test suite is fully green. The SWMR
   invariant is strongest on POSIX; AFS has its own client cache, so a live AFS
   writer/reader run is recommended before declaring full cross-host readiness.
2. **Adopting HDF5's official SWMR API** (`H5F_ACC_SWMR_WRITE/READ`). With the vlen
   column removed, this is now feasible for `data_raw_str` (it was the blocker). The
   official API gives us the same "commit = flush" semantics under HDF5's own guarantees.
   Would replace the current `H5Fflush(GLOBAL)` barrier with the API's documented
   commit/`latest_visible_row` protocol.
3. **`paths` could adopt the same 512 width** if long paths approach 256 bytes. Not
   required for SWMR (already fixed width) — only a headroom matter.
4. **Compression on `data_raw_str`.** `createOptimizedDataset` currently skips GZIP for
   string types (see `if (type_class == H5T_INTEGER || H5T_FLOAT || H5T_ARRAY)` in
   `createOptimizedDataset`); with a fixed width the column is now a compressible C1
   block if we want it. Deferred — not part of the SWMR contract.
